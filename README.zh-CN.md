# Proof-Driven Development

**你可以在 10 分钟内画出一个 Google Docs 架构。你能证明它是对的吗？**

> **架构图上随手画出黑盒子和箭头很便宜，但真正能够正确运行的系统很贵。**

[English](README.md)

大多数系统设计答案，在架构图看起来足够合理之后就结束了：

```text
Client
  ↓
WebSocket Gateway
  ↓
Collaboration Service
  ↓
Database / Cache / Queue / Snapshot Store
```

这足以解释数据流向哪里，却不足以解释：当请求重试、owner 故障切换、旧进程继续运行、快照替换历史、客户端重连、ACK 丢失，以及半年后的工程师开始“优化”实现时，系统为什么还能保持正确。

这个仓库是一个 **Proof-Driven Development** 的实验：把少量真正高影响的架构保证显式化，把它们拆成可以独立审阅的证明义务，并让这些正确性推理能够随着系统演进而被持续保留。

目标不是形式化证明每一行应用代码，而是把资深工程师平时依赖记忆反复重建的正确性推理，变成一种可以复用的工程资产。

---

## 为什么现在需要 Proof-Driven Development

AI 让实现变便宜了，但它并没有自动让可信实现变便宜。

随着代码生成吞吐量提升，一个新的瓶颈开始暴露：人仍然必须判断生成出来的系统有没有守住正确的语义。

如果每次代码审查都让资深工程师重新从头构建分布式不变量，这件事无法扩展。更高杠杆的做法，是把推理成本摊销掉：

```text
senior / staff 一次推理
        ↓
显式保证 / 证明义务
        ↓
可复用验证边界
        ↓
未来的人和 agent 重复使用
```

人的判断仍然不可替代，但它的职责会变化。工程师负责决定系统究竟承诺什么、哪些假设可以接受、哪些故障模型必须覆盖，以及什么证据强到足以相信。自动化的作用，是帮助这些判断长期被保存，而不是每次重新发现。

> **Senior 工程师发现正确性 bug；Staff 工程师尝试让这一整类 bug 更难重新出现。**

---

## 这个项目真正想验证什么？

这个仓库是一个实验，并不是在宣称这套方法已经可以普遍成立。

真正难的问题是经济性和可运维性：

1. 一个非平凡的分布式系统，能不能被拆成长期仍然容易理解的证明义务？
2. 局部证明义务能不能精确到让多个独立 AI 审计者在上面足够可靠？
3. 能不能发现规范缺口和错误分解，而不必不断重新打开整个系统上下文？
4. 实现变化能不能以足够高的召回率映射到受影响的证明义务？
5. 能不能让足够多的叶节点最终由机械证据完成验证，使这套模型降低而不是增加人工审查成本？
6. 失效传播能不能保持足够局部，让这套方法经得起真实系统持续演进？

如果这些问题的答案大多是否定的，那么 Proof-Driven Development 最终只是规范官僚主义。

如果答案大多是肯定的，那么正确性推理就可能从“上一个审阅者脑子里短暂存在过的东西”，变成可复用、可维护的工程资产。

## 核心直觉：先把推理问题变小

假设你打开一个全新的 AI agent，然后只问一句：

> 证明 `P = NP`，或者证明 `P != NP`。

我们不可能期待可见未来内有任何 agent 能把这件事情做对。提示词只有一句话，但它背后的推理空间极其巨大。

现在换一个问题：

> `1 + 1` 等于几？

一个足够强的模型在这里算错，反而会让人惊讶。

两者的提示词长度一样，但本质差异在于**推理任务的规模和歧义程度**。

真实分布式系统的正确性介于这两个极端之间。比如：

> 这个协同编辑器在重试、故障切换、重连、快照、历史压缩和 所有权并发切换下是否正确？

这个问题太大了，不能把它当成一次整体的 LLM 判断来信任。即使模型很强，它仍然要同时重建大量隐藏前提、覆盖大量故障路径，并在一个上下文里维护太多状态和语义关系。

形式化方法的做法，是把语义精确定义到足以交给证明系统或模型检查器。它可以提供更强的保证，但主要成本往往不在“跑证明”，而在于定义形式化状态空间、状态转移系统、抽象边界，以及它们和真实实现之间的对应关系。对普通生产系统来说，这个建模成本通常高到无法普遍承担。

Proof-Driven Development 想探索的是中间地带：

> **不要让一个 agent 一次推理整个系统。持续分解正确性论证，直到每一个局部证明义务都足够窄、足够明确、可以被对抗性验证，而且不容易被一个强验证器误解。**

这里并不假设任何一次局部审计是绝对不会出错的。这个方法押注的是统计和经济意义上的可靠性：当每个证明义务的语义足够精确、上下文足够小，不同的强审计者同时犯下同一种推理错误的概率，会显著低于让它们面对一个巨大的架构提示词。

Harness 的作用，就是把这种分解、上下文隔离、证明复用和重新验证系统化。

## 从架构走向证明义务

传统开发流程大致是：

```text
需求
→ 系统设计
→ 架构规范
→ 实现
→ 测试
→ 代码审查
```

正确性论证通常是隐式的。它散落在设计讨论、审阅者记忆、历史事故，以及实现过程中碰巧保留下来的假设里。

Proof-Driven Development 把这条链路显式化：

```text
工作负载 + 产品需求
        ↓
     候选架构
        ↓
    根正确性保证
        ↓
    证明义务分解
        ↓
 局部证明边界 / 假设
        ↓
       实现
        ↓
    可执行证据
```

正确性图里的节点是一个**命题**，不是服务、类、文件，也不是架构图里的方框。边表示逻辑上的证明依赖：如果某个下层命题不再可信，所有依赖它的保证都应该重新审查。

这样，正确性模型就开始有点像一个构建依赖图：

```text
语义变化
      ↓
受影响的证明义务
      ↓
传递失效
      ↓
只重新建立受影响的保证
```

编译器会在源码依赖变化后重新构建产物；Harness 尝试对正确性推理做类似的事情。

Harness 的详细语义和类型系统见 [`correctness/SPEC.md`](correctness/SPEC.md)；当前机器可读模型见 [`correctness/correctness.yaml`](correctness/correctness.yaml)。

## 为什么选择 Google Docs？

协同编辑器很适合作为案例，因为产品本身很直观，但正确性论证并不直观。

UI 层的需求听起来很简单：

> 多个用户同时编辑同一份文档，最终看到相同的结果。

但真正的架构很快会依赖一组更硬的性质：

- 已 ACK 的编辑必须在 owner 崩溃或故障切换后仍然存在；
- 重试同一个逻辑编辑不能创建第二个 canonical 操作；
- 已接受版本必须形成单一、连续、无缺口的权威历史；
- 所有权已经切换后，旧 owner 不能继续追加；
- 快照 + 回放必须重建出和权威历史相同的可观察状态；
- 重连既不能漏掉已接受变更，也不能重复应用；
- 生命周期操作不能悄悄破坏重试/恢复所依赖的 identity 或 provenance。

这些不是简单的实现细节。正是这些性质，决定了这个架构到底是不是我们以为的那个架构。

## 一个局部合理的优化，可以破坏全局证明

考虑一个简化例子。

假设每次已接受编辑都会同步更新 `documents.latest_revision`。有人发现它变成了单文档热点行，于是提出：

> 让 `accepted_changes` 成为事实来源，`latest_revision` 改成异步更新。

从数据库角度看，这听起来像一个普通的性能优化。

但假设当前正确性论证把版本前沿（frontier）当成串行化契约的一部分：

```text
追加版本 r 只有在以下条件下才能提交
pre.latest_revision == r - 1

并且提交之后
post.latest_revision == r
```

一旦 `latest_revision` 变成最终一致，它就不再能够承担这个证明责任。

这并不代表优化自动被禁止。工程师完全可以换成权威尾部查询、sequencer、锁、事务性追加原语，或者其他能够证明同一个性质的机制。

真正重要的区分是：

> **替换实现没问题；静默删除它原本承担的证明责任才是问题。**

如果没有显式正确性模型，代码审查很可能停留在：

```text
移除同步版本前沿更新
→ 降低争用
→ 看起来没问题
```

有了 proof graph 以后：

```text
版本前沿语义变化
        ↓
串行化证明义务受影响
        ↓
依赖它的保证变为 stale
        ↓
必须补充替代性的推理或证据
```

这就是 proof graph 的实际价值：审阅者不再需要先凭记忆重建整个架构，才能意识到一个看起来局部的字段其实承担着系统级不变量。

## 确定性检查，不等于规范已经完整

随着 Harness 演进，一个区别变得越来越重要：正确性模型有几种完全不同的失败方式，它们需要不同的 assurance layer。

```text
refinement
    这个 proposition / decomposition 本身是否合理？

specification coverage
    我们是不是压根漏掉了一个重要 proposition 或关系？

composition
    这些 direct premises 是否真的能推出 target？

implementation evidence
    真实系统是否满足这个 leaf proposition？
```

当相关 property 已经被明确写出来之后，第一、第三和第四类问题都可以越来越机械化；第二类问题则天然更加开放。一个 solver 无法证明“本来应该存在一个从未被建模的变量、provenance relation、terminal outcome 或 namespace coordinate”。

所以实际策略是：先用语义审计去**发现**缺失的 correctness relation，再把这些发现沉淀成以后可以由工具强制执行的 typed structure。比如，一个 provenance-sensitive state 可以显式声明自己的 resource scope 是 `document`；一旦这个语义选择被建模，Harness 就可以机械地拒绝“值字段都绑定正确、却漏掉 document namespace”的 provenance contract。类似地，一个 invariant 也可以被强制要求说明它在哪里建立，以及哪些 transition 必须持续保持它。

这个项目真正想不断推进的边界是：

> **人类/LLM 判断负责发现“什么关系重要”；typed contract、validator、signature 和机械证据负责让这个关系以后越来越难被遗忘或悄悄破坏。**

## Harness 不是为了让 LLM 变成权威

初始分解本身并不被假设为正确。它必须被持续对抗性攻击。

一个局部验证器只拿到判断当前命题所必需的上下文：目标命题、直接前提或局部证明边界、相关系统语义，以及故障模型。它的目标首先是构造反例，而不是写一篇看起来很有说服力的解释。

这个过程可能暴露不同类型的问题：

```text
缺失前提
错误依赖
一个命题打包了多个独立证明义务
遗漏生命周期状态转移
错误的 provenance 假设
系统语义本身存在真实歧义
```

上下文隔离并不意味着“短提示词就自动变成证明”。它的意义是：每个验证器面对的问题更窄，能偷偷带入未声明假设的空间更小。

Harness 再把不确定的推理步骤包在尽可能确定性的机制里面：

```text
干净上下文的局部审计
        ↓
语义判断
        ↓
类型化修改
        ↓
验证
        ↓
基于签名的失效传播
        ↓
下一批局部审计 frontier
```

已经审过的低层命题可以作为不透明契约被上层复用，而不是每次证明父命题都重新展开整棵树。如果底层语义发生变化，递归签名会自动重新打开受影响的推理。

这就是这个方法论尝试在不支付完整形式化验证的建模成本的前提下提升可靠性的地方：**让人类/LLM 的推理尽可能局部，把推理周围的控制机制尽可能确定化。**

## 证明义务最终必须接回真实实现

一个分解得再漂亮的 DAG，如果叶节点没有接到实现证据，本质上仍然只是规范产物。

不同性质应该使用不同的验证机制。一个叶节点最终可能由这些方式验证：

```text
schema / 唯一性约束
事务契约测试
控制流 / 静态数据流分析
状态机 / 属性测试
并发测试
故障注入
回放 / 差分测试
运行时不变量
model checker
```

工程问题并不是“怎么把所有东西都形式化证明”，而是：

> **对于这个特定证明义务，什么是最便宜、但保证强度足够的独立验证器？**

这个区别很重要。数据库唯一性性质不应该要求 LLM 重新读整个服务；崩溃持久性命题也不能因为代码里写着“flush”就算已经被证明。证据应该尽可能通过一个独立而经济的边界观察真实性质。

## 让 Correctness Assurance 随 Blast Radius 扩展

生产系统里存在海量特定功能行为。很多 bug 当然会伤害用户，但这不意味着它们都应该进入架构正确性 DAG。

Proof-Driven Development 更适合那些长期反复被依赖、又很容易被后续修改意外破坏的性质：

```text
幂等性
顺序性
fencing
持久性
原子状态转移
state invariant
provenance binding
快照 / 回放等价性
恢复 / 迁移安全性
```

真正有用的边界并不是“重要 bug 和不重要 bug”，而更接近：

> **这是一个稳定、高 blast radius，并且大量未来修改都必须持续守住的正确性责任吗？**

如果不是，普通测试和代码审查很可能更便宜。

范围控制只是成本模型的一半，另一半是让失效传播保持局部。

如果一个证明系统 每次改一行代码都要重新跑昂贵的全系统推理，它在经济上没有意义。

目标工作流必须是局部的：

```text
实现变化
      ↓
映射到受影响的实现影响面
      ↓
没有相关正确性证明义务？ ───→ 普通审查
      ↓
受影响的证明义务
      ↓
局部失效
      ↓
只在需要的地方重新推理 / 重新验证证据
```

绝大多数代码修改都不应该触发深度正确性工作。

维护成本应该跟 **blast radius** 走，而不是跟仓库大小或 diff 大小 走。

这也是这个项目正在验证的核心假设之一：如果任何修改最终都会让整张图失效，那么即使模型在理论上完全正确，这个方法在工程上也已经失败了。

## 这不是什么

这不是在宣称普通应用代码都应该被形式化证明，也不是说测试、代码审查可以被替代，更不是说 LLM 判断本身具有权威性。

它试图把一些已有实践接成一条更强的链：

```text
系统保证
→ 证明责任
→ 局部推理边界
→ 实现影响面
→ 独立证据
→ 变更影响
→ 定向重新验证
```

当风险和经济性值得时，形式化方法仍然是正确工具；对于大多数普通行为，普通测试仍然是正确工具。Proof-Driven Development 探索的是它们之间的空间。

## 最后的结语

十分钟画出来的架构图，可以告诉我们请求往哪里走。

真正严肃的系统设计还必须回答：当请求竞争、重试重叠、机器故障、所有权变化、快照替代历史，以及未来工程师开始优化实现以后，哪些性质仍然必须成立？

这个项目最核心的洞察是：我们并不需要一个人或 AI 一次性把整个证明都装在脑子里。

如果我们能把论证持续拆成足够小的证明义务，给每个验证器恰好需要的上下文，用多个独立视角去攻击这些证明义务，把叶节点接到真实实现证据，并在语义变化时确定性地重新打开正确的推理，那么可信的正确性推理也许可以以低得多的成本长期维护。

> **不要让一个 agent 证明整个系统是对的。构建一个证明系统，让 AI 不断回答足够小的问题，小到错误很难藏住。**
